# MewCode 上下文管理 Spec

## 背景

MewCode 当前会把工具执行结果完整写入会话历史。随着工具调用和对话轮次增加，工具结果会成为上下文 Token 的主要来源。即使请求前做了近似估算，也可能因为估算误差或单轮异常大的结果触发 Provider 的 `prompt_too_long` 错误，导致 Agent Loop 停止。

本功能为 MewCode 增加两层上下文管理能力：

- 第一层管入口：工具结果进入历史前，控制单个结果和同一条工具结果消息的体积，把超大结果外置到项目内文件。
- 第二层管累积：每次模型请求前，基于第一层处理后的正式历史估算累计 Token，在多轮对话接近窗口上限时摘要较早的 assistant/tool 内容。

两层的职责不同。第一层是预防性措施，防止一次超大工具输出直接撑爆上下文；第二层是治疗性措施，防止许多未超过单条限制的小结果在几十轮对话中累积超限。第二层估算到的历史必须始终是第一层处理后的最终形态。

如果请求已通过两层前置检查但 Provider 仍返回 `prompt_too_long`，系统还要执行一次有界的恢复流程：强制压缩、用新的历史重试原请求；恢复失败后按正常错误流程结束。

现有 Provider 能返回 API usage。本功能不引入精确 tokenizer，而是使用最近一次 Provider usage 作为估算锚点，仅对其后的消息增量按字符数近似估算。

## 目标

- 在默认 128,000 Token、或 Provider 自行配置的上下文窗口内，尽量保持 Agent Loop 连续工作。
- 单个工具结果超过 50,000 字符时，不把完整内容写入对话历史。
- 单条工具结果消息超过 200,000 字符时，从最大结果开始外置，直到最终消息回到限制以内。
- 外置结果保留前后各 2,000 字符预览、绝对文件路径和原始长度，并可由现有 `ReadFile` 能力重新读取。
- 重量摘要固定包含五个部分：用户目标与约束、已完成工作与关键决策、当前代码/文件状态、未完成事项与下一步、重要工具结果文件索引。
- 保留所有用户原始消息，不由摘要模型改写；近期消息从尾部向前保留，直到同时满足约 10,000 Token 和至少 5 条消息。
- 支持 `/compact` 强制压缩；自动摘要连续失败三次后熔断自动路径。
- 对明确的 `prompt_too_long` 错误执行一次 13,000 Token 安全余量的 `ForceCompact`，然后以同一轮、同一用户请求重试；再次超限则按正常错误流程结束。

## 功能需求

### F1：上下文预算配置

系统为每个 Provider 支持独立的上下文窗口配置；未配置时使用 128,000 Token 默认值。

- 自动重量压缩使用窗口上限前 13,000 Token 的安全余量。
- 用户执行 `/compact` 时使用窗口上限前 3,000 Token 的安全余量。
- 因 `prompt_too_long` 触发的恢复性压缩使用 13,000 Token 安全余量。

### F2：单个工具结果外置

工具结果写入会话历史前，若单个结果超过 50,000 字符，系统必须：

1. 将完整结果写入当前会话的项目内上下文目录。
2. 用前 2,000 字符、后 2,000 字符和中间省略标记构成预览。
3. 在历史中只保存预览、绝对文件路径和原始字符长度。
4. 确保模型可通过现有文件读取能力重新读取完整结果。

不超过 50,000 字符的单个结果不因该规则被外置。

### F3：单条工具结果消息聚合限制

一轮并行工具调用形成一条 user 工具结果消息时，系统必须在消息进入历史前计算其最终体积。

如果总量超过 200,000 字符，系统按原始结果大小从大到小依次外置结果，直到最终写入历史的消息不超过 200,000 字符。处理后的预览、路径和长度也计入最终消息体积。

### F4：第一层结果成为正式历史

第一层处理必须发生在工具结果写入会话历史之前。

进入历史的工具结果只能是未超过限制的完整结果，或已外置后的预览、路径和长度。第二层估算、后续 API 请求和摘要输入都只能读取这份处理后的正式历史，不得重新使用已经外置的完整结果。

### F5：请求前累积 Token 估算

每次正常 API 请求前，系统必须按以下顺序执行：

1. 确认工具结果已经完成第一层处理。
2. 估算待发送上下文的累计 Token，至少包含正式历史，并计入本次请求附带的系统提示、工具定义和 reminder。
3. 如果存在上一次 API usage，以它作为估算锚点，只对本次上下文增量按字符数近似换算。
4. 增量近似换算使用“字符数 / 3.5”，不使用精确 tokenizer。
5. 如果没有可用 usage 锚点，则对当前待发送上下文做完整近似估算。
6. 如果估算值超过上下文窗口减去 13,000 Token，触发第二层重量压缩。

每次 LLM 请求结束时，系统必须从流尾 usage 事件捕获并汇总以下字段，作为下一次估算的真实 Token 锚点：

`input + cache_read + cache_creation + output`

Provider 未返回的 cache usage 维度按 0 计入。摘要请求同样更新内部锚点，但不计入 Agent Loop 轮次或正常 TUI Token 用量。

### F6：重量压缩范围

重量压缩发生时，系统必须：

- 将较早的 assistant/tool 内容整理为摘要。
- 保留所有用户原始消息，不以摘要文本替换或改写。
- 从历史尾部向前保留近期原文，直到同时满足约 10,000 Token 和至少 5 条消息。
- 用压缩后的摘要和近期原文替换可压缩的较早 assistant/tool 内容。
- 如果没有可压缩的较早内容，则报告无需压缩，不伪造摘要。

### F7：结构化摘要生成

摘要必须使用当前选中的 Provider 和模型生成，摘要请求的工具列表必须为空。

摘要 Prompt 必须明确要求：

- 禁止调用任何工具。
- 先完成内部分析草稿，再输出正式摘要。
- 分析草稿只用于当前生成过程，不得写入会话历史、文件或用户可见输出。
- 正式摘要固定包含以下五部分：
  1. 用户目标与约束
  2. 已完成工作与关键决策
  3. 当前代码/文件状态
  4. 未完成事项与下一步
  5. 重要工具结果文件索引

### F8：摘要边界消息

重量压缩完成后，系统必须追加一条边界消息，明确告知模型：

- 摘要只代表历史概况，不是完整代码内容。
- 需要文件细节时必须重新读取对应文件。
- 不得根据摘要臆测代码、工具输出或文件内容。

### F9：Provider 硬超限恢复

如果正常对话请求已经通过前置检查，但 Provider 返回 `prompt_too_long`：

1. 丢弃本次失败请求的半截流式响应，不写入不完整 assistant 消息。
2. 立即执行一次使用 13,000 Token 安全余量的 `ForceCompact`。
3. 压缩成功后，用新的历史重试原来的请求。
4. 重试属于同一 Agent Loop 轮次，不重复写入用户消息，不增加迭代次数。
5. 如果压缩失败，或重试仍返回 `prompt_too_long`，按现有错误流程结束。
6. 该恢复路径最多执行一次，不得无限重试。

其他普通 Provider 错误不触发该恢复路径。

### F10：手动压缩

用户输入 `/compact` 时，系统必须强制执行一次重量压缩，不要求当前已经达到自动阈值。

- 手动压缩使用 3,000 Token 安全余量。
- 成功后向用户报告压缩结果。
- 当前没有可压缩内容时向用户报告无需压缩。
- 手动压缩失败时向用户报告失败原因，但不把完整工具结果重新写回历史。

### F11：自动摘要熔断

自动重量摘要连续失败 3 次后，系统必须熔断自动摘要路径：

- 后续自动请求不再反复触发摘要。
- 如果估算仍然超出可用预算，直接按上下文错误结束，不调用原模型请求。
- 用户仍可通过 `/compact` 显式重试。
- 任意一次摘要成功后，连续失败计数清零。
- 熔断只针对当前会话，不影响新会话。

### F12：上下文文件生命周期

外置结果文件必须存放在当前项目的 `.mewcode/context/<会话目录>/` 下。

- 文件在当前会话期间保持可读。
- MewCode 正常退出时删除当前会话目录。
- 不把外置结果、摘要缓存或上下文压缩状态持久化为下一次会话的历史。
- 清理失败不能阻止其他资源继续关闭，并应记录安全错误信息。

## 非功能需求

### N1：数据保真

- 用户原始消息必须逐字保留，不因摘要而改写。
- 外置文件必须保存完整工具结果，不得只保存预览。
- 预览生成规则必须稳定：前后各 2,000 字符，中间使用明确省略标记。
- 同一批并行工具结果在历史中的顺序必须与模型发起调用的顺序一致。

### N2：历史一致性

- 第一层处理和工具结果写入历史必须是一个不可被其他请求观察到中间状态的原子操作。
- 第二层只能读取第一层处理后的正式历史。
- 摘要完成前不能删除旧历史；摘要成功后才能一次性替换可压缩内容。
- 取消、Provider 错误或摘要失败不得留下半截 assistant 消息、悬空工具调用或部分压缩历史。

### N3：估算约束

- 不引入精确 tokenizer 或机器学习估算器。
- 估算始终基于最近一次 LLM 请求真实 usage 锚点和后续消息增量。
- 每次 LLM 请求结束都必须更新内部锚点，包括摘要请求。
- 摘要请求的 usage 不得改变 Agent Loop 轮次或正常 TUI Token 用量。

### N4：性能与调用次数

- 工具结果未超过第一层限制时，不产生额外摘要 LLM 调用。
- 对话未达到重量压缩条件时，不产生额外摘要 LLM 调用。
- 第一层只执行本地字符统计和文件写入，不调用 LLM。
- Provider 正常接受请求时，不因上下文管理额外重复发送该请求。
- `prompt_too_long` 恢复最多增加一次摘要调用和一次原请求重试。

### N5：安全与隐私

- 外置文件只能写入当前项目的会话上下文目录，并使用现有文件读取边界。
- API key、Authorization、工具结果中的敏感信息不得出现在新增日志、错误提示或调试输出中。
- 摘要 Prompt 必须禁止调用工具，摘要模型不能借此执行文件、命令或其他外部操作。
- 正常退出时清理当前会话的上下文文件，不清理其他会话或用户已有文件。
- 文件清理失败不得扩大删除范围，也不得阻止其他资源关闭。

### N6：兼容性

- 未增加上下文窗口配置的旧 Provider 配置继续可用，并使用 128K 默认值。
- 上下文管理未触发时，现有 Provider 请求格式、工具执行、权限判断、取消、轮次上限和 TUI 行为保持不变。
- 摘要调用失败或自动熔断时，系统仍按既有安全错误流程收口，不绕过 Provider、权限或工具边界。

### N7：有界失败

- 自动摘要失败连续达到 3 次后，自动路径必须停止尝试。
- 同一次原请求最多执行一次 `ForceCompact` 恢复重试。
- 摘要请求不能递归触发新的摘要请求。
- 任何失败路径都必须最终结束当前操作或返回可继续输入的明确错误状态，不能阻塞或无限循环。

### N8：可观测性

- 用户能看到手动压缩成功、无需压缩或失败的结果。
- 发生 `prompt_too_long` 恢复时，用户能看到系统正在压缩并重试，而不是看到无原因的重复请求。
- 外置结果的路径、原始长度和预览必须能被后续模型请求看到。
- 错误信息应能区分普通 Provider 错误、摘要失败、文件写入失败和二次上下文超限，同时不泄露敏感值。

### N9：可测试性

- 字符阈值、Token 安全余量、尾部保留规则、失败次数和重试次数必须是确定性的。
- 第一层、第二层、摘要调用、Provider 超限恢复和 `/compact` 都应能在不依赖真实外部 API 的情况下测试。
- 必须覆盖“小结果累积触发第二层”和“大结果第一层外置但第二层不触发”这两个相反场景。
- 必须通过 tmux 运行真实 MewCode，验证工具调用、压缩、重试和最终回复的完整链路。

## 不做的事

- 不引入精确 tokenizer、第三方 tokenizer 服务或机器学习 Token 估算。
- 不根据历史效果自动学习或动态优化摘要策略。
- 不允许用户配置 50,000/200,000 字符阈值；这两个阈值固定在功能中。
- 不对普通用户消息做第一层外置；第一层只处理工具结果。
- 不改写、重排或删除用户原始消息。
- 不实现跨进程、跨会话的对话历史恢复。
- 不保留上一会话的外置结果、摘要缓存或失败计数供下一会话使用。
- 不把外置结果写入项目外目录，也不新增绕过现有路径边界的读取权限。
- 不为摘要增加独立 Provider、独立模型或独立凭据配置。
- 不允许摘要模型调用任何工具。
- 不因普通 400、认证失败、限流、网络错误或模型不存在错误触发 `ForceCompact`。
- 不对 `prompt_too_long` 无限重试；不实现多级递进重试策略。
- 不实现自动重连、后台定时压缩、跨会话清理或上下文文件持久化管理。
- 不改变现有工具执行、权限确认、取消、Provider 协议和 Agent Loop 的既有语义。
- 不实现基于语义重要性的消息筛选、摘要质量评分或摘要版本合并。

## 验收标准

### 预算与第一层预防

- AC1：Provider 未配置上下文窗口时，系统按 128,000 Token 运行；配置了 Provider 窗口时，使用该 Provider 的配置值。
- AC2：单个工具结果为 50,000 字符或更少时，完整结果进入历史。
- AC3：单个工具结果超过 50,000 字符时，完整结果写入当前会话目录，历史只包含前后各 2,000 字符预览、绝对路径和原始长度。
- AC4：通过历史中的路径调用现有文件读取能力，可以读回外置结果的完整内容。
- AC5：同一条工具结果消息超过 200,000 字符时，系统按结果大小从大到小外置，直到最终历史消息不超过 200,000 字符。
- AC6：第一层处理完成后，历史中不再出现已外置结果的完整文本。

### 第二层累积治疗

- AC7：连续产生 20 个均未超过 50,000 字符的工具结果时，第一层不外置；累计上下文接近窗口上限时，第二层在下一次 API 请求前触发。
- AC8：单个 80,000 字符工具结果被第一层外置，且整体上下文未接近窗口上限时，第二层不触发摘要。
- AC9：第二层估算使用最近一次 Provider usage 中 `input + cache_read + cache_creation + output` 的总和，并按后续新增内容的“字符数 / 3.5”估算增量。
- AC10：每次 LLM 请求结束后，包含摘要请求，都能从流尾 usage 事件更新内部估算锚点。
- AC11：自动压缩在窗口上限前 13,000 Token 触发；`/compact` 使用 3,000 Token 安全余量并强制执行。

### 摘要与历史保留

- AC12：重量压缩后，所有用户原始消息内容逐字不变。
- AC13：重量压缩从历史尾部保留原文，直到同时满足约 10,000 Token 和至少 5 条消息。
- AC14：摘要包含五个固定部分：用户目标与约束、已完成工作与关键决策、当前代码/文件状态、未完成事项与下一步、重要工具结果文件索引。
- AC15：摘要请求没有任何工具定义；摘要 Prompt 明确禁止工具调用，并要求先生成内部草稿再输出正式摘要。
- AC16：摘要草稿不会出现在会话历史、文件或用户可见输出中。
- AC17：压缩后存在边界消息，提醒模型需要文件细节时重新读取，不得根据摘要臆测代码。
- AC18：摘要调用产生的 usage 不计入 Agent Loop 轮次或正常 TUI Token 用量。

### 硬错误恢复与熔断

- AC19：正常请求收到 `prompt_too_long` 时，系统丢弃失败请求的半截响应，执行一次 13,000 Token 余量的 `ForceCompact`，然后重试原请求。
- AC20：恢复性重试与原请求属于同一 Agent Loop 轮次，不重复用户消息、不增加迭代次数。
- AC21：重试仍返回 `prompt_too_long` 时，系统按正常错误流程结束，不再次压缩或重试。
- AC22：摘要自动失败连续达到 3 次后，自动压缩停止；估算仍超限时直接报错，不调用原模型请求。
- AC23：自动熔断后，用户仍可通过 `/compact` 显式发起压缩尝试；摘要成功后连续失败计数清零。

### 文件、安全与兼容性

- AC24：外置文件位于 `.mewcode/context/<会话目录>/`，当前会话可读，MewCode 正常退出后被清理。
- AC25：文件写入、摘要调用或清理失败时，不把完整超大结果重新放回历史，不泄露敏感值，并能继续关闭其他资源。
- AC26：在上下文管理未触发时，现有 Provider 请求、工具执行、权限、取消、轮次限制和 TUI 行为保持不变。
- AC27：用户能看到 `/compact` 的成功、无需压缩或失败结果，以及 `prompt_too_long` 正在压缩并重试的状态。

### 自动化与端到端

- AC28：单元测试覆盖第一层两个阈值、预览、文件读回、第二层尾部保留、五段摘要、usage 锚点、三次熔断和一次重试限制。
- AC29：集成测试验证 Provider 返回 `prompt_too_long` 后能完成压缩并用新历史重试。
- AC30：执行全量 Gradle 测试，项目编译和全部测试通过。
